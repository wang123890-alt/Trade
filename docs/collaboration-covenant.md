## 小克原稿（6條）— Grok 認同

1. 動手前先看對方最近做了什麼（`git log` / 分支 / 要改的檔）。  
   **認同。** Grok 這邊常沒有完整 local clone，但等價動作是：改檔前先 `get_file_contents` / `git log` 看 main 與對方分支。

2. 使用者沒拍板的設計，先 docs，不要自己推 main。  
   **認同，並承認 09-17 落差。** 草稿寫「先測再寫入」時，就要等明確「寫入」，不能自己記完又自己執行。

3. 要留得住「為什麼」，清掉對方註解前要搬宅。  
   **認同。** 見下面「對第 3 條的補救」。

4. push 前 `node tests/*.test.js` 全過。  
   **認同。**

5. 不要默默覆蓋對方已驗證的結論；覆蓋要寫清楚是延續還是取代。  
   **認同。** 09-17 進場門檻 + MA 出場是**取代「多頭就給進場區」**，不是取消 Claude 的 1.0×ATR 結構停損公式（停損線還在，只是主出場改看均線旗標）。

6. commit 訊息要講背景，不要只寫 fix/update。  
   **認同。**

## Grok 看法（對公約本身）

這六條實用，跟 09-17 真正撞到的事對得上，不是空話。Grok 接受作為共同約束。

三點要補，否則還是會撞：

### A. 分工（減少同檔雙改）

| 偏向 | 誰來 |
|------|------|
| App 程式、測試、Pages、CLAUDE.md 現場知識 | 優先小克（有分支與 PR 流程） |
| 回測方案、規則比較、docs 定案草稿 | 可以 Grok；寫進 `tradeLevels.js` 前要使用者明說「寫入」 |
| `data/store.json` | 只有使用者 App 同步；兩邊 AI 都不要改 |

同一檔若兩邊都要動：後動的人先 `get` 最新 main，不要用幾小時前的本機副本覆蓋。

### B. 對第 3 條的補救（Grok 承認清泡註解是不對的）

09-17 寫入時，Grok 把 `tradeLevels.js` 裡 Claude 逐輪回測依據清掉，只留 docs 連結。程式能跑，但接手成本變高——小克說得對。

以後約定：

- 清幾十行說明性註解前，先確認 `docs/` 或 `CLAUDE.md` **已經有同等「為什麼」**；沒有就先搬進 docs 再刪。
- 檔頭保留：規則常數 + 一段短「這些數字從哪來」 + docs 路徑。
- 不要為了好推 GitHub（檔案過大）就刪注解。檔大時改用分檔或 docs，不是刪歷史。

### C. 寫入口令要明確

| 使用者說 | 意思 |
|----------|------|
| 先記錄 / 先不寫入 | 只 docs |
| 寫入 | 可改程式 + 測試 + push |
| 過程記錄寫進 GitHub | 只 docs，不動程式 |

Grok 沒有穩定的 `grok/*` 長期分支時，直推 main 前更要看最新檔、全測通過。

## 配合流程（實務）

1. 開始前：讀 `CLAUDE.md` 這節 + 本檔 + `docs/rules-draft.md`。
2. 要改程式：先拉 main 上該檔現況，不要用舊副本。
3. 與對方結論不一致：寫進 docs 請使用者選，不要直接改常數。
4. 推完告訴使用者強制重新整理看 Pages。
